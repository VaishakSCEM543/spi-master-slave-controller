# 01 — Project Definition

## What This Project Is

This is an **8-bit SPI Master–Slave Controller** designed from scratch using synthesizable Verilog RTL.

The goal was not to *use* SPI by configuring a microcontroller peripheral.  
The goal was to *design the SPI hardware itself* — the same kind of hardware that sits inside a microcontroller chip.

---

## The Problem Statement

Suppose you have two digital devices that need to exchange data quickly and reliably:

```
Device A (Master)       Device B (Slave)
    STM32              Sensor / Memory / DAC
       │                        │
       └──────── ? ─────────────┘
          How should they communicate?
```

They need a communication protocol — a set of agreed-upon rules that defines:

- When a bit is sent
- When a bit is sampled
- Who controls timing
- How the start and end of a transfer are signalled

**SPI (Serial Peripheral Interface)** is one such protocol.

---

## Why SPI?

| Need | SPI Solution |
|---|---|
| High-speed data transfer | Dedicated clock line, no arbitration overhead |
| Full duplex | Separate MOSI and MISO lines |
| Simple interface | 4 wires: SCK, MOSI, MISO, CS |
| Multiple peripherals | Shared bus + individual CS per device |
| Synchronous transfer | Clock generated by master, no baud-rate matching |

---

## Why RTL? (Not Software SPI)

There are two completely different ways to use SPI in an embedded system:

```
Approach A — Software using existing hardware
─────────────────────────────────────────────
STM32 CPU
  │
  ├── Configure SPI peripheral registers
  ├── HAL_SPI_Transmit(...)
  └── Hardware does the work

Approach B — Designing the hardware itself (this project)
──────────────────────────────────────────────────────────
Design and implement:
  ├── Shift registers
  ├── Bit counter
  ├── FSM controller
  ├── Clock divider
  └── Structural wiring
```

In **Approach A**, you configure existing SPI hardware that someone else designed.  
In **Approach B** (this project), you *are* the hardware designer.

This distinction is fundamental in VLSI/FPGA/RTL engineering interviews.

---

## Why FPGA?

FPGA stands for Field-Programmable Gate Array.

When you write Verilog RTL, you are describing digital hardware behavior.  
An FPGA lets you convert that description into actual hardware:

```
Verilog RTL (this project)
        │
        ▼
   Synthesis tool (Vivado)
        │
        ▼
  Flip-flops, LUTs, routing
        │
        ▼
      FPGA bitstream
        │
        ▼
   Physical FPGA chip
        │
        ▼
  Real SPI signals on real pins
```

This project is currently at the **simulation stage**. Physical FPGA validation is future work.

## Current Project Scope

| Scope Item | Decision |
|---|---|
| Data width | 8 bits (fixed) |
| SPI Mode | Mode 0 (CPOL=0, CPHA=0) |
| Bit order | MSB first |
| Transfer type | Full duplex |
| Architecture | 1 master, 1 slave |
| Clock domain | Single (all logic on system clock) |
| SCLK source | Register toggled by master FSM — not a separate clock domain |
| Verification | Behavioral simulation, self-checking testbench |
| FPGA validation | Not yet completed |

## What I Learned Building This

This project taught me the difference between:

- **Using** a protocol (writing firmware)
- **Designing** a protocol controller (writing RTL)

Building it meant understanding what actually happens at every clock edge:  
which flip-flop updates, which bit shifts, which signal drives the line.

That level of understanding is what this repository is built around.
